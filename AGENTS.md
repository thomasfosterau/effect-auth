# AGENTS.md

General guidance for any coding agent working here; Claude Code reads it through [.claude/CLAUDE.md](.claude/CLAUDE.md), which imports it with [CONTRIBUTING.md](CONTRIBUTING.md) and [README.md](README.md). effect-auth is a library monorepo: authentication and authorization for [Effect](https://effect.website/) v4, as nine publishable `@thomasfosterau/effect-auth*` packages under `packages/*`. It has no application, no deployment and no secrets.

Every package publishes `dist/`. Every package except the Svelte binding and the two Alchemy packages peers `effect` through `catalog:peers`; `alchemy-cloudflare` and `alchemy-postgres` peer it, and their Alchemy peers, through `catalog:alchemy-peers` (`^4.1.0`, because `alchemy` requires `effect ^4.1.0`); the binding peers its framework and `effect` (`catalog:peers`, for the Atom types it adapts; it imports nothing from `effect` at runtime). Which code gets a package of its own is [ADR-0022](docs/adr/0022-package-boundaries.md): merge into core unless the package brings a dependency the core lacks (the owner's own libraries count as dependencies, runtime platforms don't), split Alchemy packages per Alchemy provider, and the owner decides vendor-adapter merges case by case. The archetype decides what a package may import:

| Archetype              | Packages                                            | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core**               | `effect-auth` (`@thomasfosterau/effect-auth`)       | Depends on `effect` only (optional peers: `@thomasfosterau/effect-jsonapi` for `./http`, `@node-saml/node-saml` for `./saml`). Flat root modules for the spine (sessions, users, the authorization kernel: `Policy`, `Condition`, `Entity`, `Authorizer`, `Rbac`, …) plus lowercase cluster directories (`email/`, `http/`, `oauth/`, `password/`, `plugins/`, `multifactor/`), each with a subpath export, and the subpath-only tiers the root never loads: `http/`, `client/` (the browser client, plus `./client/atoms`, the session as `effect/reactivity` Atoms and the one client entry that imports `effect` at runtime, and `./client/testing`, the in-memory server fixture), `sql/` (every store it covers over `effect/sql`) and `saml/` (the `SamlVerifier` over node-saml; Node-only). `./ladder` (`src/Ladder.ts`) imports nothing, not even `effect`, because browser bundles load it; `ModuleGraph.test.ts` enforces this and that the root reaches neither the subpath-only tiers nor node-saml. |
| **Storage adapters**   | `drizzle`, `alchemy-cloudflare`, `alchemy-postgres` | Implement the core's store contracts (`SessionStore`, `UserStore`, `ApiKeyStore`, …) over a database, or wire the core's `/sql` stores to one. The database library is a **peer**, never bundled. The Alchemy packages are split per Alchemy provider: `alchemy-cloudflare` (D1, built on `@alchemy.run/cloudflare`'s services: its D1 access runs on `Cloudflare.D1.QueryDatabase`, its deploy-time schema is an Alchemy Action, never raw workerd types; ADR-0023) and `alchemy-postgres` (Postgres over Hyperdrive or a URL, peers `@effect/sql-pg`; named for the database because no `@alchemy.run/*` provider gives it anything to depend on).                                                                                                                                                                                                                                                                                                                                                              |
| **Vendor adapters**    | `argon2`, `resend`, `twilio`                        | Implement one core seam (`PasswordHasher`, `EmailSender`, `SmsSender`) over one vendor. Plain `fetch` against the vendor's REST API rather than an SDK where possible; Workers-safe.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Framework bindings** | `svelte`                                            | A thin binding over the core's `/client` and its session Atoms (`/client/atoms`). The framework and `effect` (types only) are peers.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Server bindings**    | `sveltekit`                                         | The server side of one framework, over core's session-resolution seam ([ADR-0021](docs/adr/0021-sveltekit-server-adapter.md)). Typed structurally against the framework's request event, so it takes no framework dependency; `effect` is its peer.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

Before adding a package, check ADR-0022: code that needs only `effect` (or a dependency the core already has) is a core subpath instead, with an `exports` entry, a `.fallowrc.json` `entry`, a section in the core README and its rules in the core `AGENTS.md`. A new package picks an archetype, gets a `vite.config.ts` that declares its tasks through `packageTasks` ([vite.tasks.ts](vite.tasks.ts)), its own `AGENTS.md` (boundary, invariants, terms) with a one-line `CLAUDE.md` that imports it (`@AGENTS.md`), a row in the root `README.md`, its entry points and a zone (or a place in its archetype's zone) in [.fallowrc.json](.fallowrc.json), its `#build` edge in the root `test:coverage` task (`vite.config.ts`), its `check:dist` target (and the peers to install beside it) in `scripts/check-dist.ts`, and a changeset. An Alchemy package also joins CI's `alchemy` job and the `--exclude` of its runtime suite in `test:coverage`.

## Common pitfalls

- **Never depend on legation**, in any package and in any dependency field, dev dependencies included. effect-auth may depend on effect-jsonapi. [docs/BOUNDARY.md](docs/BOUNDARY.md) holds the reason and the full rules.
- **Importing the core package root never pulls the HTTP tier** (`http/`, and through it `effect/http-api` and effect-jsonapi) into a consumer's module graph: the tier is published only on the `./http` subpath (#205), and `ModuleGraph.test.ts` fails on any root-reachable import of either. Don't re-export anything from `http/` at the root. The same holds for `client/`, `sql/` and `saml/` (which may reach the HTTP tier themselves), and for `@node-saml/node-saml`, the optional peer only `./saml` imports.
- **Every external version lives in the catalog** in [pnpm-workspace.yaml](pnpm-workspace.yaml) (`catalogMode: strict` rejects anything else). After editing it, run `pnpm install` and commit `pnpm-lock.yaml`, or CI fails with `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`. `effect` is a singleton (`overrides`); its published floor lives in `catalogs.peers`, and the Alchemy packages' own in `catalogs.alchemy-peers`, beside their exact `alchemy` / `@alchemy.run/cloudflare` pins. The rule for every `effect` / `@effect/*` peer: `^4.0.0` unless a dependency forces more, or the package's own code needs an Effect unstable/experimental module that first shipped in a later minor (name it in the catalog comment). Here both are `^4.1.0`: the core's `effect/crypto` (new in Effect 4.1), and for the two Alchemy packages also their `alchemy` peer, which peers on `effect ^4.1.0`. Dependabot ([dependabot.yml](.github/dependabot.yml)) groups only the sets that must move together (`toolchain`: `vite-plus`, `vitest`, `@vitest/*`, `@effect/tsgo`; `effect`: `effect` + `@effect/*`, `@effect/docgen` included; `svelte`; `alchemy`: `alchemy` + `@alchemy.run/*`) into one PR, every other dependency getting its own, with a 1-day `cooldown` against pnpm's `minimumReleaseAge` of 480 minutes (8 hours). By hand, because Dependabot cannot: the npm-alias entries (`vite`, which must equal `vite-plus`, and the `typescript` / `@typescript/native` pair), an `@effect/tsgo` whose `components` table covers a new `vite-plus`'s oxlint, the exact `alchemy` / `@alchemy.run/cloudflare` peers in `catalogs.alchemy-peers` (to the release the applications pin), and the advisory floors under `overrides` (`brace-expansion@5`, `js-yaml@3`, …), which you raise or drop when `pnpm audit` or their dependents move.
- **Every adapter depends on the core as `"@thomasfosterau/effect-auth": "workspace:^"`** (#631), a regular `dependency` that publishes as a caret range, so package managers dedupe to one copy of the core within a 0.x minor. Never `workspace:*`, which publishes an exact pin and leaves an adapter running its own nested, unpatched core. Under 0.x a caret covers one minor only, so release the adapters with every core minor.
- **Each Alchemy package's `AuthSchema.test.ts` is its own task.** Those are the suites that load the alchemy runtime, so they live in `test:alchemy` (with alchemy-postgres's `Postgres.test.ts`, which needs a server), run by CI's separate `alchemy` job ("Alchemy runtime"), not in `test:unit`. Don't skip them. A cached task sees only the environment variables it declares, so alchemy-postgres's `test:alchemy` declares `DATABASE_URL` and `CI` (`packageTasks`' `extra` as `{ command, env }`); under `CI` a missing `DATABASE_URL` fails its server cases instead of skipping them (#766). alchemy 2.0.0-beta.85 is the first release on Effect 4.1's `effect/crypto` modules (beta.84 and earlier import `effect/Crypto`, which 4.1 removed, #499), so `catalogs.alchemy-peers` pins `alchemy` there.
- **TypeScript is split 6/7.** `typescript` in the catalog is an alias for TS6 (the JS compiler API, bin `tsc6`) because `svelte-check`, `@effect/docgen` and the editor language service all `require("typescript")` and TS7 ships no JS API. `@typescript/native` is TS7 (bin `tsc`), which every package's `build` and `check` script runs; the root `prepare` script patches it, and `vite-plus`'s oxlint, with `@effect/tsgo` (`effect-tsgo patch --typescript --oxlint`; the patched oxlint carries the `effecttsgo` plugin the lint config extends, and stock oxlint rejects the config). `@effect/tsgo`, `@typescript/native` and `vite-plus` move as a set of three, kept inside the `components` table in `node_modules/@effect/tsgo/dist/effect-tsgo.cjs`: that table lists the TypeScript and oxlint versions each `@effect/tsgo` release supports, and `vite-plus` pins the oxlint. Read it before bumping any of them, since the patch hard-errors at install on a TypeScript it has no artifact for. Never bump `typescript` itself to 7 (Dependabot proposes exactly that, and it breaks every JS-API consumer).
- **`@effect-diagnostics` directives are read by the patched `tsc`, and only in the unprefixed form:** the rule name, then the severity, as in `// @effect-diagnostics-next-line multipleEffectProvide:off` (`packages/alchemy-cloudflare/src/AuthSchema.test.ts`). The `effect/<rule>:off` form that `@effect/language-service`'s README shows is silently ignored by the `@effect/tsgo`-patched TS7 `tsc` (checked against `@effect/tsgo` 0.46.1).

## Conventions

- **Optional properties are `?: T | undefined`.** `exactOptionalPropertyTypes` is on (`tsconfig.base.json`), so a bare `?: T` rejects a caller that forwards its own optional value.
- **Relative imports carry the `.ts` extension** (`rewriteRelativeImportExtensions`).
- **Effect's helper modules are namespace imports under their canonical aliases** (`effect/prefer-namespace-imports`, at `error`): `import * as Arr from "effect/Array"`, `P` for `Predicate`, `R` for `Record`, `Str` for `String`, `Eq` for `Equal`, `Bool` for `Boolean`, and `Option` / `Schema` by name. Every other module comes from the barrel (`import { Effect, Layer } from "effect"`). JSDoc `@example`s follow the same rule.
- **Tests import from `vite-plus/test`**, never `vitest`; lint (`vite-plus/prefer-vite-plus-imports`) rejects the direct import.
- **Lint extends `@effect/tsgo/oxlint-presets`' `recommended` and `@enfect/oxlint`'s `recommended`** (the `effect/*` rules) in the root `vite.config.ts`, over oxlint's `correctness`, `suspicious` and `perf` categories with the `typescript`, `unicorn`, `oxc`, `import`, `promise`, `vitest` and `jsdoc` plugins, type-aware. A rule is turned `off` only with a comment giving the convention it contradicts; the overrides scope the platform-service rules off for Node-only code (tests, `testing/`, scripts, configs) and the `effect`-module rules off for code that imports no `effect` (the Svelte binding, `./ladder`). The Effect preset's ported-code allowances (#443) are paid down; the oxlint "adoption allowances" (#503) sit at `warn` for code that predates them; a new site is a defect, and a rule whose count reaches zero has its line deleted so it is back at `error`. Fix findings by changing the code, never with a disable comment.
- **Services are `Context.Service` classes with a static `layer`**, and dependencies are resolved at layer construction so service methods carry `R = never`.
- **Errors follow [DESIGN.md](docs/DESIGN.md) D4:** domain errors are `Data.TaggedError`; HTTP-boundary errors in `http/HttpApiSchema.ts` are `Schema.TaggedError` classes with a status. HTTP is `effect/http-api`.
- **Secrets are compared with `constantTimeHashEqual` / `timingSafeEqualBytes`** (`src/TokenHash.ts`) and randomness comes from the `SecureRandom.SecureRandom` service (`effect/crypto`; default `PlatformCrypto.layer`); direct `node:crypto` use stays corralled in `password/Password.ts`, `TokenHash.ts` and `Cipher.ts`.

## Commands

The commands (`vp install`, `vp check` vs `vp run check`, `check:dist`, `docs`, `test:coverage`, fallow, `pnpm changeset`) and what each needs are in [CONTRIBUTING.md → Commands](CONTRIBUTING.md#commands). ## Verification

Before you report work as done, run the gates below in order and quote each command with its final pass/fail. If a gate can't run here, say which and why in the PR body; never imply it ran. Steps 1–8 are CI's order ([ci.yml](.github/workflows/ci.yml), job `test`):

1. `vp run build`
2. `vp check` (after the build: type-aware lint reads the siblings' `dist/`)
3. `vp run docs`
4. `vp run check:dist`
5. `vp run check:dist -- --effect catalog`
6. `vp run check`
7. `vp run -r test:unit`
8. `pnpm audit --audit-level high` (network)
9. `vp run test:coverage`, then `vp exec fallow audit --format json --quiet --explain --gate-marker agent --base origin/trunk` (the fallow gate below; not a CI step). `fallow audit` reads `coverage/coverage-final.json` and never refreshes it, so run `test:coverage` first.

CI's second job, `alchemy` ("Alchemy runtime"), runs `vp run --filter @thomasfosterau/effect-auth-alchemy-cloudflare --filter @thomasfosterau/effect-auth-alchemy-postgres test:alchemy`.

## Branches and pull requests

The branch, rebase, squash-merge and changeset rules are in [CONTRIBUTING.md → Branches and pull requests](CONTRIBUTING.md#branches-and-pull-requests). On top of them, an agent:

- opens the PR without being asked once a branch has a pushed commit, watches it to merge or close (CI failures, review comments), and keeps the body current: what changed and why, which gates ran with their result, the changesets added;
- never publishes or versions by hand: the Release workflow opens the version PR (`chore: version packages`) and the owner merges it;
- writes to `thomasfosterau/effect-auth` only, passing `-R thomasfosterau/effect-auth` whenever the cwd might be another checkout.

## Work tracker

Issues are the backlog: when you find work you can't do now, file an issue rather than leaving a TODO; a TODO in code cites its issue (`TODO(#205)`). The issue is the spec — read its comments (`gh issue view <n> --comments`); later comments override the body, and its code claims need re-checking against current `trunk`. Record decisions and findings as issue comments. Stop-and-report is a valid outcome: on a blocker outside the issue's scope, comment the evidence on the issue and stop. Scope cut mid-PR becomes a linked issue before merge.

## Effect

Read the installed package before writing Effect code: `node_modules/effect/AGENTS.md` and `node_modules/effect/ai-docs/` (the pinned version ships both), the declarations in `node_modules/effect/dist/*.d.ts` and the source in `node_modules/effect/src`. Never guess at an Effect API: v4 renamed much of v3. The pinned version is the `effect` entry in `pnpm-workspace.yaml`'s catalog; the published floor is `catalogs.peers.effect`.

## Fallow local gate

Before any `git commit` or `git push`, run `fallow audit --format json --quiet --explain --gate-marker agent --base origin/trunk`. If the verdict is `fail`, fix the reported findings before retrying. Treat JSON runtime errors like `{ "error": true, ... }` as non-blocking. Audit defaults to `gate=new-only`: only findings introduced by the current changeset affect the verdict.
