# Auth as an internal Worker on Alchemy, with Postgres over Hyperdrive

This recipe deploys effect-auth as its own Cloudflare Worker, reachable only over a service
binding from your app's Workers, and storing its data in Postgres through Hyperdrive. The
infrastructure is declared in Alchemy. [Auth as a separate service](split-auth-service.md)
covers the protocol side of the topology: the transport, session resolution, and the `Set-Cookie`
relay. This guide covers the deployment.

## 1. Storage: Hyperdrive at runtime, the origin URL on deploy

`@thomasfosterau/effect-auth-alchemy/postgres` is the Postgres counterpart of the package's D1
wiring. Install its optional peer, `@effect/sql-pg`, alongside it.

**In the auth Worker**, provide every store over the Hyperdrive binding:

```ts
import * as Postgres from "@thomasfosterau/effect-auth-alchemy/postgres";

const stores = Postgres.layer(env.HYPERDRIVE);
```

`@effect/sql-pg` connects with `node:net` and `node:tls`, so the Worker needs the `nodejs_compat`
compatibility flag. Hyperdrive pools connections at the edge, so keep the client's own pool small.
`Postgres.layer(env.HYPERDRIVE, { maxConnections: 1 })` is enough for one request at a time.

**In the Alchemy program**, declare the `AuthSchema` resource and give its provider the origin
database. A Hyperdrive binding exists only inside a Worker, so the deploy-time provider connects
to the origin directly:

```ts
import { AuthSchema, AuthSchemaProvider } from "@thomasfosterau/effect-auth-alchemy";
import * as Postgres from "@thomasfosterau/effect-auth-alchemy/postgres";

const providers = Layer.mergeAll(
  Cloudflare.providers(),
  AuthSchemaProvider({ database: Postgres.database(Redacted.make(process.env.DATABASE_URL)) }),
);
// …inside the program:
yield * AuthSchema("auth-schema");
```

Every deploy reconciles the `auth_*` tables in Postgres. The DDL is idempotent `CREATE … IF NOT
EXISTS`, and the tables are dropped only with `dropOnDelete: true`.

### Living with drizzle-kit migrations

An app whose migrations are generated by drizzle-kit can own the auth tables in either of two
ways. Choose one, not both:

- **`AuthSchema` owns them.** Keep the `auth_*` tables out of your Drizzle schema, or declare
  them with `tablesFilter: ["!auth_*"]` in `drizzle.config.ts`, so drizzle-kit neither generates
  nor drops them. `AuthSchema` reconciles them on each deploy.
- **Your migrations own them.** Put effect-auth-sql's `schemaStatements` into a custom
  migration (`drizzle-kit generate --custom`), keep the tables out of drizzle-kit's diff as above,
  and don't declare `AuthSchema`. On each effect-auth-sql upgrade, add the statements it gained to
  a new custom migration.

The first keeps the auth schema in step with the library version you deploy. The second keeps one
migration history.

## 2. The auth Worker is internal-only because it declares `workersDev: false`

```ts
const auth =
  yield *
  Cloudflare.Worker("auth", {
    main: "./src/auth.ts",
    // Load-bearing: without it the Worker is public. See below.
    workersDev: false,
    // …the Hyperdrive binding, the secrets below, `compatibility.flags: ["nodejs_compat"]`
  });
```

**Declaring no `domain` or `routes` is not what keeps the Worker private.** Alchemy defaults
`workersDev` to `true`, and on every deploy it attaches a `<name>.<account>.workers.dev` URL and a
preview URL per version unless `workersDev: false` is passed. A Worker with no route is still a
published Worker. Nothing marks the mistake either: an exposed Worker looks exactly like a
private one with the `workersDev` line missing. Pin it with a test that reads your `alchemy.run.ts`
or the deployed Worker's settings.

Pass `false`, not the object form. `{ enabled: false }` leaves `previewsEnabled` at its default,
`true`, and every deployed version is then reachable at its own preview URL.

This matters more here than for a Better Auth Worker, because effect-auth's handler serves more.
Beyond sign-in and session reads it mounts `/api-keys`, `/admin`, SCIM and the organization
endpoints. When the OIDC provider is configured it also mounts the token endpoint and dynamic
client registration. An accidental `workers.dev` URL on that handler exposes much more than the
equivalent mistake on Better Auth's.

### The consuming Workers

Each app Worker that needs a session gets a **service binding** to the auth Worker, and
reaches it through `Http.RemoteSession` ([the split-service guide](split-auth-service.md)):

```ts
const auth = Http.RemoteSession.make({ fetcher: env.AUTH, prefix: "/api/auth" });
```

The app's public origin must be in the auth Worker's `trustedOrigins`, because the browser's
`Origin` header arrives at the auth Worker through the app.

### Secrets

Set these as Worker secrets, never as plain bindings:

- the database password, inside the Hyperdrive origin;
- `SessionCacheConfig.secret`, the HMAC key of the cookie cache, when the cookie cache is on. Use
  a high-entropy value and rotate it by bumping `SessionCacheConfig.version`;
- the OAuth client secrets and the JWT signing keys you configure.

## 3. What the handler serves, and what may face the internet

If you want a public auth origin instead (the app's browser talks to the auth Worker directly),
this is what you would be exposing. The paths are relative to the handler's `prefix`.

| Group                             | Paths                                                                                                                                                                                        | Intended exposure                                                                                                                                                                                                                                                        |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Sign-in and sign-up               | `POST /sessions`, `POST /users`, `/second-factor-challenges/*`, `/otp-challenges`, `/password-resets`, `/email-verifications`, `/google-one-tap-nonces`                                      | Public. These are what a browser calls. Put the rate limits (`ipRateLimit`, which needs `trustedProxy`) and the captcha plugin in front of them.                                                                                                                         |
| Session and account               | `/sessions`, `/sessions/*`, `/multi-session/*`, `/users/*`, `/identifiers`, `/identifiers/*`, `/email-changes/*`, `/account-deletions/*`, `/multi-factor-enrollments/*`, `/backup-code-sets` | Public, and authenticated by the session cookie.                                                                                                                                                                                                                         |
| SSO as a relying party            | `/sign-in/sso`, `/sso/callback`, `/sso/saml/*`                                                                                                                                               | Public: the identity provider sends the browser back here. `/sso/register` configures a provider and belongs with admin.                                                                                                                                                 |
| API keys                          | `/api-keys/*`                                                                                                                                                                                | Authenticated by a session, so it may be public. Many deployments keep key management internal.                                                                                                                                                                          |
| Organizations, teams, invitations | `/organization/*`, `/organizations`, `/teams/*`, `/invitations/*`                                                                                                                            | Public and session-authenticated, if your product exposes them.                                                                                                                                                                                                          |
| Admin                             | `/admin/*`                                                                                                                                                                                   | Internal. Authorized by role, but there is no reason to route it publicly.                                                                                                                                                                                               |
| SCIM                              | `/Users`, `/Groups`, `/Schemas`, `/ResourceTypes`, `/ServiceProviderConfig`                                                                                                                  | Reachable by the identity provider that provisions users, and nothing else. Bearer-token authenticated.                                                                                                                                                                  |
| JWT                               | `/token`, `/jwks`                                                                                                                                                                            | `/jwks` is public wherever another service verifies the tokens. `/token` exchanges a session for a JWT, so it is as public as the session routes.                                                                                                                        |
| OIDC provider and device grant    | `/oauth2/*`, `/register`, `/register/:clientId`, `/.well-known/*`, `/device/*`                                                                                                               | Public only when you act as an identity provider: clients call them directly. Dynamic client registration (`/register`) needs `trustedProxy` for its rate limit and is safest left off unless you need it. `/oauth2/clients` is client administration: keep it internal. |

An internal-only auth Worker sidesteps the table: nothing is public, and the app decides which
operations to forward.
