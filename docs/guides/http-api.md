# The HTTP API

The `/http` subpath: building the handler, sign-up attributes, every endpoint it serves, and running auth as a separate service.

## Services that build asynchronously: `Http.makeAsync`

`Http.make` is synchronous, so it can throw only when the `services` build finishes before it returns. It runs the build the way `Effect.runSync` does, and the build is still running when `make` returns if it waits on:

- asynchronous work, such as a database connection or `Effect.promise`;
- a merged layer (`Layer.merge`, `Layer.mergeAll`) whose build yields, or runs past Effect's per-slice operation budget (2,048 operations by default), since each merged layer builds on a fiber of its own;
- a forked fiber that yields before it completes a `Deferred` the build awaits;
- a finalizer that does asynchronous work, when the build fails.

For those, `make` cannot throw: the same checks fail the handler's build instead, and every request rejects with the error. `Http.makeAsync` takes the same options and waits for the build however it is composed. It resolves to the same `{ handler, dispose }`, serving that one build, and rejects with the errors `make` throws, so the app fails to start. Before it rejects, it releases what the build acquired and waits for every finalizer, asynchronous ones included.

```typescript
import * as Auth from "@thomasfosterau/effect-auth";
import * as Http from "@thomasfosterau/effect-auth/http";

// `services` connects to a database while it builds.
const { handler, dispose } = await Http.makeAsync({
  services, // with a RateLimiter merged in
  trustedProxy: Auth.ClientIP.cloudflare,
});
```

To keep `Http.make` and have it refuse a build it cannot finish, set `strict: true`. `make` then throws `ServicesBuildPendingError` (also exported as `Http.ServicesBuildPendingError`) when the `services` build has not finished by the time it has run the build synchronously, so the app fails to start; the error's message names `Http.makeAsync`. Before it throws, `make` interrupts the build and releases what the build acquired, as far as that runs synchronously. Two parts finish after `make` has thrown: a finalizer that does asynchronous work, and, when the build is in an uninterruptible step that waits on asynchronous work (an `Effect.acquireRelease` acquire that awaits), the whole release, since the interrupt waits for that step to end. A build that was failing when `make` threw (a step that failed while a finalizer it runs awaits) ends with that failure, which `make` logs with `Effect.logError`, since `ServicesBuildPendingError` cannot carry it. A build that finishes synchronously is unaffected: `make` throws the startup errors or the build's own failure, or returns the handler, as without the option. `Http.makeAsync` ignores the option, since it waits for the build whatever it says.

```typescript
// Throws ServicesBuildPendingError if `services` cannot finish building synchronously.
const { handler } = Http.make({ services, trustedProxy: Auth.ClientIP.cloudflare, strict: true });
```

## Sign-up attributes

A sign-up never sets an attribute that carries authority. Whatever reaches it, `EmailPasswordService.signUp` (and so `UsernameService.signUp`) and `AuthLifecycleService.signUp` drop, after the `beforeSignUp` hooks, the `UserService`'s server-only attributes (`UserServiceConfig.serverOnlyAttributes`, default `["role"]`) and `Auth.SIGN_UP_PROTECTED_ATTRIBUTES`: the ban keys (`banned`, `banReason`, `banExpires`), the SCIM keys (`scimUserName`, `scimDeactivated`, `scimExternalId`), the managed-user stamp (`provisionedBy`) and `isAnonymous`. Set those once the user exists, through their own door (`AdminService.setRole`, `banUser`, SCIM provisioning). `EmailPasswordService` reads `UserService`'s list when `UserService` is in context as its layer is built; `AuthLifecycleService` always does.

Over HTTP, `POST /users` keeps only the `attributes` keys you list in `signUpAttributes`. The default is none:

```typescript
const { handler } = Http.make({
  services,
  // A sign-up may set these two; any other key it sends is dropped.
  signUpAttributes: ["plan", "locale"],
});
```

A key the list doesn't name is dropped without an error, so a client that sends one still signs up, and the answer doesn't tell a caller which keys the server guards; the user in a `201` shows what was kept. Naming a server-only, ban or SCIM key here has no effect. The kept attributes may take at most `Http.SIGN_UP_ATTRIBUTES_MAX_BYTES` (4096) bytes as UTF-8 JSON; a larger bag is refused with `400`. Dropped keys don't count, and the whole request body stays under `maxBodySize` (default 64 KiB). `groupLayers(cookie, multiSession, signUpAttributes)` takes the same list when you compose the contract yourself.

## HTTP endpoint reference

The included HTTP API speaks [JSON:API](https://jsonapi.org/) through `@thomasfosterau/effect-jsonapi`, an optional peer that only the `./http` subpath needs. Every endpoint is one of two tiers ([ADR-0024](https://github.com/thomasfosterau/effect-auth/blob/trunk/docs/adr/0024-json-api-http-tier.md)): a JSON:API resource operation, or an endpoint whose wire format another specification fixes. The paths below are relative to the mount prefix (`/api/auth` by default). Upgrading from routes that are gone: the [migration guide](https://github.com/thomasfosterau/effect-auth/blob/trunk/docs/guides/jsonapi-migration.md) maps every old endpoint to its replacement.

### JSON:API resources

These take and answer `application/vnd.api+json` (a request with another media type is `415`, an `Accept` that excludes it `406`) and fail with JSON:API error documents (`Http.JsonApiErrors`: `status`, `detail` the message, `meta` carrying the `message` and, when there is one, the stable `code`). The resources are declared once, in `Http.Resources`.

No response body carries a session token. Every `sessions`, `device-sessions` and `impersonations` resource is named by the session's stored id, the SHA-256 digest of its token, which is not a credential: `GET /sessions/:id`, `DELETE /sessions/:id` and the `device-sessions` actions take it. The token itself reaches the client only in the `HttpOnly` session cookie and, when `cookie.bearerMode` is on (`"always"`, or `"opt-in"` for a request sending `x-use-bearer: 1`), in the `set-auth-token` response header, which a native client stores and presents as `Authorization: Bearer <token>`.

A session-store or user-store fault is a logged `500`, never a `401`: only a session that is absent, expired, banned or whose user is gone is `401`, so a database outage does not read as a mass sign-out in the browser client. The same holds for `AuthMiddleware` in an app's own `HttpApi`. `OptionalAuthMiddleware` serves an absent or refused session as anonymous and a fault as a `500`, unless `Http.optionalLayer(config, { onDegraded })` is given: then the request is served as anonymous and the fault goes to `onDegraded`, as `SessionResolution.resolveFailOpen` requires.

Every response that carries `Set-Cookie` is sent with `Cache-Control: no-store`: sign-in and sign-up, a sign-out or account change that clears the cookies, and `GET /sessions/current` when it refreshes the `cookie.cache` cookie, the one `GET` that sets a cookie. A `Cache-Control` that already has `no-store` is kept; one without it keeps its directives and gets `no-store` appended, which a cache honours whatever else the header says. The bodies that hand a credential over are `no-store` too, cookie or not: `GET /sessions/:id`, `POST /tokens`, `POST /api-keys`, `POST /multi-factor-enrollments`, `POST /backup-code-sets`, `POST /oauth-clients`, `POST /device/token`, `POST /oauth2/token`, `GET /oauth2/userinfo` and `POST /register`. `Http.RemoteSession.relayResponse` and `withSetCookie` apply the same rule to the responses they relay.

### The RFC tier

These keep the wire format their specification fixes, and are never JSON:API documents: an OAuth client, an IdP or a SCIM provisioner built to the specification would not accept one, so "finishing the conversion" here would break every conforming peer. They are the `auth` and `scim` groups of the contract. `OpenApi.test.ts` checks that none of them declares `application/vnd.api+json` (and that every resource group does), and each endpoint's suite pins its media type.

`Http.groupLayers` is every group of the contract with the JSON:API protocol middleware on the resource groups, for serving `AuthApi` from your own `HttpApiBuilder`.

## Auth as a separate service (`RemoteSession`)

`Http.RemoteSession` resolves the session from an app edge over a service binding or any fetch-alike (`make`, `resolveAtEdge`, `resolveAtEdgeFailOpen`) and relays `Set-Cookie`; the [split-service guide](https://github.com/thomasfosterau/effect-auth/blob/trunk/docs/guides/split-auth-service.md) walks through it. A request carrying an API key resolves the key instead, through `GET /api-keys/current`: the result is `{ session: None, user, apiKey, credentialClass: "machine" }`, `apiKey` holding the key's public fields only. The cookie is not forwarded on that call and never stands in for the key: a `401` is anonymous, and any other answer (the `404` of an auth service without an `ApiKeyService`, a `429`) fails `resolveAtEdge` closed and degrades `resolveAtEdgeFailOpen` to anonymous. **Each resolution consumes one use of the key** (`remaining` decrements, `lastUsedAt` moves). Pass the auth service's `cookie.apiKeyHeaders` as `credentials.apiKeyHeaders` so both read the same header.
