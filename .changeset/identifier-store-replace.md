`IdentifierStore.replace(from, to)` swaps one of a user's identifiers for a new value: it claims `to` and releases `from` as one change, so the user is never left holding neither. A store with transactions writes both at once; a store without them claims `to` before it releases `from`. It resolves to the replacement, or `null` when the user does not hold `from`, and fails with `AuthError` when another user holds `to`'s value, as `create` does. `replace` is a required member of the contract, so a custom `IdentifierStore` implements it (see `docs/guides/byo-stores.md`). `memoryIdentifierStore` and `IdentifierStoreKV` implement it, and `replaceInputError` gives an implementation the shared refusal for a `to` with another user, another type, `from`'s own id or the same value. Of two concurrent replaces of the same `from`, the in-memory store lets one succeed; `IdentifierStoreKV` checks `from` before it writes and releases it unguarded, so both can succeed and leave the user holding both new values.

`replaceIdentifier(store, from, to)` calls it with readable failures: `IdentifierTakenError` when another user holds the value, `IdentifierNotFoundError` when the user does not hold `from` (including when the store refused `to` because a concurrent replace of `from` already gave the user that value), `AuthError` for other store failures.

`AccountManagement.confirmEmailChange` changes the user's email of record through `replaceIdentifier`, then releases any other email the user holds; a user with no email claims the new one. If the email of record changes during the confirmation, it succeeds when the user already holds the new address (a double-submitted confirmation) and otherwise fails with `AccountTokenError`, keeping the token. A user with no email whose claim finds the address already theirs succeeds the same way, and in every case the new address ends verified. It works on every identifier store, including one that holds a single email per user (#381).
