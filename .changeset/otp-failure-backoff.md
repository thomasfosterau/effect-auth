Security fix (#590): email and phone OTP sign-in could be brute-forced, because each resend issued a fresh code with a fresh attempt counter, so `maxAttempts` bounded one code and nothing bounded an address. Every wrong code is now also counted against the (address, purpose) pair in a failure budget that a resend, an expiry or the attempt limit never resets, and `send` backs off once it grows: after `backoff.freeFailures` wrong codes (default 5), `send` fails with `ResendTooSoonError` until `backoff.baseDelay` (default one minute), doubled for each further wrong code and capped at `backoff.maxDelay` (default one day), has passed since the latest one. A successful verification resets the count. There is no lockout: once the delay has passed a send goes through, so an attacker can slow an address's owner down but not lock them out. Under the defaults an attacker gets 18 guesses at an address in the first day and 3 a day after that, where before there was no limit. The backoff applies alike to an address with and without an account. `resendCooldown` now defaults to 60 seconds for `EmailOtpConfig` and `PhoneOtpConfig` (was off; `0` turns it off). Codes stay 6 digits.

Breaking: `EmailOtpStore` and `PhoneOtpStore` gain `getFailures`, `recordFailure(address, purpose, at)` and `clearFailures`, over the new `OtpFailures` type (`{ count, lastFailureAt }`; the three methods are `OtpFailureBudget<Purpose>`), with `OtpBackoffConfig` for the new `backoff` option. A store keeps the budget apart from the code's record, so `upsert`, `delete` and `purgeExpired` leave it, and should make `recordFailure` one atomic statement. `EmailOtpStoreKV` keeps it under `email-otp-failures:<purpose>:<email>`, and `./sql` in the new `auth_email_otp_failures` table, which `migrate` (and so effect-auth-alchemy-cloudflare's `AuthSchema` on the next deploy) creates. `./testing` adds `emailOtpStoreConformance` and `phoneOtpStoreConformance`, `memoryPhoneOtpStore` and `memoryOtpFailures` (the budget's three methods, to spread into a store of your own). Migration: implement the three methods on a custom store and run the new conformance suite against it; run `migrate` once on a SQL database; a caller that sent twice in a row on purpose passes `resendCooldown: 0`.
