Security fix (#586): an organization invitation can no longer be accepted with an unverified email identifier on the invitation id alone. An attacker could sign up with an invitee's address (unverified, with a session by default) and accept the invitation, joining at the invited role, owner or admin included. Now each invitation carries a secret 256-bit token, stored only as its SHA-256 digest (`Invitation.tokenHash`) and handed to `sendInvitationEmail` for the link; presenting the token is the proof of the address. `acceptInvitation(userId, { invitationId, token, currentSessionId? })` and `rejectInvitation(userId, { invitationId, token })` take it, and a wrong or missing token answers "Invitation not found". Acceptance still works for apps that run without email verification: when the matching email identifier is unverified, the token is its first proof and goes through the same path as a magic link or an email OTP (#440), clearing the account's password and revoking every session but `currentSessionId` before the identifier is marked verified. `resendInvitation` mints a new token, so the link sent earlier stops working.

Breaking: `sendInvitationEmail` now receives `{ invitation, organization, token }` (`InvitationDelivery`) and is required to invite or resend (without it `inviteMember` refuses). `OrganizationService.layer` now also requires `EmailPasswordStore` and `SessionService`. Store implementations persist the new `tokenHash` field. Over HTTP, `PATCH /invitations/:id` to `accepted` or `rejected` takes the token as the input-only `token` attribute (`400` without it or with a wrong one); the client's `organization.acceptInvitation(invitationId, token)` and `rejectInvitation(invitationId, token)` take it as a second argument, and `./client/testing`'s `makeServerFixture` exposes the delivered tokens as `sentInvitations`.
