# @thomasfosterau/effect-auth-drizzle

`SessionStore`, `UserStore` and `IdentifierStore` (plus a single-table `IdentifierStore`), and `EmailPasswordStore` / `PasswordResetUserStore`, `UserServiceStore` (#728), `ApiKeyStore`, `RateLimitStore` and the email-verification / password-reset token stores (#675), over Drizzle ORM for PostgreSQL, SQLite and MySQL, batched `Request` reads, and drizzle renderings of two kernel projections (`ladderCheck`, `ownedListFilter`).

## Boundary

Archetype **Storage adapter** (`.fallowrc.json` zone `storage-adapters`, which may import `core` and `ladder`). Peers: `effect` and `drizzle-orm` (`catalog:drizzle-peers`, `>=1.0.0-rc.5 <2`: the 1.0 line only, #735, which every `1.0.0-*` from `rc.5` up and every 1.x satisfy, the commit-suffixed `1.0.0-rc.5-<sha>` builds included; the catalog pins the tagged `1.0.0-rc.5` the declarations are built on; 0.4x was dropped because its column types differ from 1.0's and no one `.d.ts` serves both). Depends on `@thomasfosterau/effect-auth` through `workspace:^`, so it publishes as a caret range (#631). The package never opens a connection and bundles no driver: the consumer hands over a drizzle handle through `databaseLayer` / `effectDatabaseLayer`. PGlite, `better-sqlite3` and `pg` are dev dependencies for the suites only. It stands alone: it does not wrap effect-auth/sql.

## Invariants

- **One store implementation serves all three dialects.** It uses only the query-builder fragment `PgAsyncDatabase`, `SQLiteAsyncDatabase` and `MySqlAsyncDatabase` spell identically (`AuthDatabase` in `Database.ts`), each call ending in `.execute()`. No `RETURNING` (MySQL has none): `setVerified` updates, then re-reads; the one exception is the rate-limit upsert below, which falls back to a read on MySQL.
- **No `any` in the public surface**: row and insert types derive from the tables passed in; `defineSchema` checks column mappings at the type level (`ColumnKey`).
- **Promise and Effect drivers are one code path.** A query's result is `Promise<A> | Effect<A>`; the stores run in the caller's fiber, so an application's `db.transaction` on an Effect driver covers every store call (`Transaction.test.ts`). A handle may be an `Effect` that yields it, run once per query, for request-scoped pools (required on Workers).
- **Store contract**: a miss is `null`, a delete of a missing row is a no-op, a driver failure (unique violation included) is `AuthError` with the cause. Core's `claimIdentifier` / `replaceIdentifier` turn the race into `IdentifierTakenError`. The single-table store's refusals of what it cannot hold (a second email, any other type) are `IdentifierRefusedError`, which SCIM answers with `409 uniqueness`.
- **`(type, value)` is unique** on the identifiers table; `IdentifierStore.replace` claims the new value before deleting the old one and opens no transaction of its own.
- **Identifier values compare byte for byte on every dialect** (#602). MySQL's `identifiers.value` is `binaryVarchar` (`varchar(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin`) in the table and in `migrationStatements`. An application's own identifier column (single-table `users.email`, a `defineSchema` value column) needs the same collation, which the README states. `binaryVarchar` is a `customType` (it predates 1.0's `varchar().collate()`, which declares the same column). The contract suites' "differ only by case or accent" case pins it on PostgreSQL and SQLite; `MySqlSchema.test.ts` pins the MySQL DDL.
- **Session ids are token digests** computed by the service; `UserStore` never reads or writes `password_hash`.
- **`migrationStatements` / `migrationSql` match the drizzle tables** per dialect (`*Schema.test.ts`), and are generated from one column spec per table in `Ddl.ts` with a per-dialect type map (the drizzle tables stay per dialect: their builders share no type); MySQL declares indexes inline (no `CREATE INDEX IF NOT EXISTS`) and uses `varchar(255)` so the unique index is legal.
- **The published declarations are built, and checked, against drizzle-orm 1.0** (#735). The source names only types 1.0 exports (`PgAsyncDatabase`, `SQLiteAsyncDatabase`, `MySqlAsyncDatabase`, `AnyRelations`) and reads rows through `InferSelectModel` / `InferInsertModel`, since 1.0's base `Table` has no `$inferSelect` / `$inferInsert`. `vp run check:dist` type-checks a consumer of the packed `dist/` (the README's `defineSchema` example, a consumer `select().from(Pg.identifiersTable)`, `databaseLayer` over a real handle of each dialect) without `skipLibCheck`, on the peer floor and catalog version (`1.0.0-rc.5`, the tagged rc the declarations are built on) and on the applications' commit build (`drizzleApplicationsPin`, `1.0.0-rc.5-ab785fc`, whose own build of the declarations would fail on the tagged rc); only errors inside drizzle-orm's own declarations are tolerated. The mysql-proxy fixtures pass mysql2's codecs (`src/testing/MySqlProxy.ts`), since 1.0's proxy decodes nothing; suites pass clients as `drizzle({ client })`.
- **Batched reads keep store semantics** (dedupe, coalesce into one `IN (...)`, `null` on a miss, identifiers ordered by `createdAt`), and the store contracts never use them. `Requests.test.ts` pins query counts through drizzle's `logger`.
- **`ownedListFilter` agrees with `Auth.OwnedAccess.canView`** row for row (`OwnedListFilter.test.ts`, on Postgres); the follow set stays a subquery and an unrenderable one fails closed.
- **The stores beyond sign-in keep their contracts' guarantees on default tables** (#675). `EmailPasswordStore` is the only store that reads or writes `password_hash`; `UserStore`'s projection drops a mapped `passwordHash`. `RateLimitStore.increment` never reads-modifies-writes: an `UPDATE` re-opens an expired window, then an upsert adds one, so concurrent callers get distinct counts. `RateLimitStore.purgeExpired(tables)` is the only thing that deletes a row nobody asked to delete: one `DELETE` of the rows whose `reset_at` and `blocked_until` have both passed (#686). The upsert is the one dialect-specific statement: `DrizzleInsertValues` carries `onConflictDoUpdate` (PostgreSQL, SQLite, with `RETURNING`) or `onDuplicateKeyUpdate` (MySQL, count read back). API keys and tokens are stored only as the digests core computes; the tokens table serves `EmailVerificationStore` and `PasswordResetStore` by `purpose`, and every read and delete is scoped to it. Only `EmailPasswordStore` and `UserServiceStore` take a `defineSchema` mapping (the former its `passwordHash`, both the promoted columns); `ApiKeyStore`, `RateLimitStore` and `TokenStore` take a dialect's `Tables`. `UserServiceStore` keeps core `/sql`'s semantics: `get` is `UserStore`'s projection, `update` is one `UPDATE` writing the user whole (`name` / `image` `NULL` when absent, `updatedAt`, the bag; each promoted column its value or `NULL`), splitting attributes with `EmailPasswordStore`'s `splitAttributes` (no mapped bag → `AuthError`), and returns its input, a missing user included; `delete` removes the user row only. It is not in `layer()`, like the other stores beyond sign-in. `src/testing/AuthStoresContract.ts` runs all five on PGlite (Promise and Effect drivers) and better-sqlite3, with core's `apiKeyStoreConformance`; `AuthStores.mysql.test.ts` pins the MySQL SQL.
- **The README's sign-up writers are compiled and run**: `src/testing/readme/*Writer.ts` hold them between `README:begin` / `README:end` markers, and `ReadmeSignUpWriter.test.ts` checks the README shows each verbatim. Edit both together.

## Terms

- **Dialect namespace** — `Pg`, `Sqlite`, `MySql`: `tables`, `defineTables(names)`, `migrationStatements`, `migrationSql`.
- **Auth schema** — `defineSchema({ sessions, users, identifiers })`: the stores pointed at an application's own tables by column mapping; `fromTables` is the identity mapping.
- **Promoted attribute** — a user attribute kept as a real column (`users.role`), surfaced in `user.attributes` under its name; the column is the only authority for that key.
- **Single-table identifiers** — `SingleTableIdentifierStore`: one email per user, read from and written to the application's `users` row.
