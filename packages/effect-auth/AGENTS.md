# @thomasfosterau/effect-auth

The headless core: sessions, users and identifiers, every sign-in method, multi-factor, OAuth, organizations, admin, API keys, JWT, SSO, SCIM, the OIDC provider and the authorization kernel, as Effect services and layers, plus four opt-in subpaths the root never loads: the HTTP tier (`./http`), the browser client (`./client`, with its session Atoms `./client/atoms` and its `./client/testing` fixture), SQL storage over `effect/sql` (`./sql`) and the Node-only SAML verifier (`./saml`). Client, SQL and SAML were their own packages until ADR-0022 merged them in.

## Boundary

Archetype **Core** (`.fallowrc.json` zone `core`, which may import only `ladder`). Peer: `effect` (`catalog:peers`); optional peers `@thomasfosterau/effect-jsonapi` (only `./http`, and `./client/testing` through it) and `@node-saml/node-saml` (only `./saml`, at `^5.1.0`); no `dependencies` at all. Never a dependency on legation in any field ([docs/BOUNDARY.md](../../docs/BOUNDARY.md)); effect-jsonapi is allowed. Every other package in the workspace builds on this one, so a breaking export change here reaches all eight. A module that needs only `effect` (or a dependency the core already has) belongs here as a subpath, not in a new package ([ADR-0022](../../docs/adr/0022-package-boundaries.md)).

Layout: flat root modules for the spine (`SessionService`, `SessionStore`, `UserStore`, `Identifier`, `TrustedDevice`, `SessionContext`, `SessionResolution`, `SessionCookies`), the authorization kernel (`Entity`, `Condition`, `Policy`, `AuthorizationModel`, `PolicyStore`, `Authorizer`, `Rbac`, `Permission`, `System`, `Guard`, `OwnedAccess`, `ReferenceAccess`, `Cacheability`, `Protected`, `OrganizationEntities`, `Ladder`, `LadderSchema`) and the unclustered features (`Organization`, `Admin`, `ApiKey`, `Jwt`, `OidcProvider`, `Sso`, `Saml`, `Scim`, `Delivery`, `KeyValueStores`, `RateLimit`, …). Lowercase cluster directories each have an `index.ts` barrel, a subpath export and a root namespace:

## Invariants

- **`./ladder` imports nothing**, not even `effect`: browser bundles load it. `ModuleGraph.test.ts` pins it; `.fallowrc.json` gives `Ladder.ts` its own zone with no outbound rule.
- **The root barrel must not pull the HTTP tier** (`http/`, `effect/http-api`, effect-jsonapi) into a consumer's graph: the tier is published only on the `./http` subpath (#205), and `ModuleGraph.test.ts` fails on any root-reachable import of either. It reaches none of `client/`, `sql/` and `saml/` either; those may reach the HTTP tier (`./client` does, for its wire types) and the rest of the core, through relative imports.
- **The HTTP tier is JSON:API, except the RFC tier** ([ADR-0024](../../docs/adr/0024-json-api-http-tier.md)): every endpoint this library designs is a resource operation in `Http.Resources` / `HttpApi.ts` answering `application/vnd.api+json`, and the `auth` and `scim` groups keep the wire formats their specifications fix (RFC 8628, OAuth 2.0 / OIDC, RFC 7591 / 7592, RFC 8414, RFC 7517, the SSO bindings, SCIM 2.0). Never move an endpoint across that line. `http/OpenApi.test.ts` pins both sides, each RFC-tier suite pins its media types (`src/testing/WireFormat.ts`, test-only), and `client/ClientRoutes.test.ts` fails on a client call to a route the contract does not serve. A new endpoint is a resource unless a specification fixes its format.
- **`@node-saml/node-saml` is reached only from `./saml`**: `ModuleGraph.test.ts` asserts the root never reaches it (nor `xml-crypto`). `./saml` is Node-only, so the README and its module docs say so; the rest of the core stays Workers- and browser-safe.

### `./client`

- **`client/Client.ts` has no runtime imports**, and `./client` (`client/index.ts`) re-exports nothing else. It imports the HTTP tier with `import type` only (`ModuleGraph.test.ts` pins both), so nothing server-side and no Effect runtime reaches a browser bundle that loads only `./client`. `./client/atoms` (`client/SessionAtoms.ts`) is the one client entry that imports `effect` at runtime (`effect`, `effect/reactivity` and `./Client.ts`, pinned too); it is a subpath of its own, never re-exported from `./client`, so the Effect runtime is opt-in (#206). Only `./client/testing` imports the core at runtime. The package `tsconfig.json` adds the `DOM` lib for them (`window`, `document`, `BroadcastChannel`).
- **One method per contract endpoint, named after it**, typed with the contract's own payload and view types, so a contract change is a compile error here. Optional server modules answer `404`; a method existing does not mean the server mounted the feature.
- **Every request sends `credentials: "include"`**; a non-2xx rejects with `AuthClientError` carrying `status` and the server's JSON `message` (else the status text). JSON is detected by the media-type essence (`application/json` or `+json`), not a substring.
- **The client never holds a session token.** The token lives in the `HttpOnly` cookie; every `SessionView` id the client reads (and the cross-tab broadcast posts) is the stored id, which `revokeSession` and `multiSession.setActive` / `revoke` take (#581).
- **The client holds no session state.** Session-changing calls go through `mutating`, which runs the call, then every `onSessionChange` listener, and resolves once their promises settle (`Promise.allSettled`: a listener's rejection never fails the call). `invalidateSession()` notifies without a call.
- **The session is an Atom graph** (`makeSessionAtoms`, `effect/reactivity`), and commands stay plain client calls the Atoms observe. The read is lazy: the first registry read or mount starts `GET /sessions/current?include=user`; it starts waiting (`isPending: true`); a `401` is `data: null`, not an error; a transient failure keeps the last `data` (the `AsyncResult`'s previous success) and sets `error`; a superseded refetch is interrupted, so an out-of-order result is dropped. The `onSessionChange` listener exists only while the session is mounted, so session-changing calls refetch only while observed; the read itself is `keepAlive`, so a later subscriber starts from the last read without a request. Derived Atoms forward `refresh` to the read. A session change propagates through the graph (`SessionAtoms.test.ts` pins it); nothing keeps an invalidation list.
- **Background refresh is opt-in and degrades to a no-op** outside a browser (`makeSessionAtoms`'s `refresh`: `intervalMs`, `onFocus`, `crossTab` via `BroadcastChannel`); it lives in the observed Atom's lifetime, so it starts with the first subscriber and stops with the last. A cross-tab message replaces the shown session without a request and is not echoed; a waiting or failed read keeps what is shown.
- **SSR hydration of the session Atoms is not implemented** (follow-up to #206, to match `@legation/svelte/kit`'s shape).
- **The second-factor continuation refuses an expired challenge locally**, without a request; the server enforces expiry regardless.
- **`./client/testing` runs the real `Http.make` handler** over in-memory stores with features off by default (so unconfigured endpoints answer `404`), and `makeCookieJarFetch` emulates the browser's cookie jar. It is published.

### `./sql`

- **Supported dialects are SQLite (D1 included) and PostgreSQL.** Every statement must run on both. MySQL is not supported (#260): it has no `ON CONFLICT`. Don't add per-dialect branches; point MySQL users at effect-auth-drizzle. No driver is a dependency or a peer: the consumer provides a `SqlClient` layer (`@effect/sql-pg`, `@effect/sql-sqlite-*`, the D1 client in effect-auth-alchemy-cloudflare); PGlite and `better-sqlite3` are dev dependencies for the suites only. The two Alchemy packages build on this subpath, so a change to a table or a statement here is a change to every D1 and Alchemy Postgres deployment too.
- **`schemaStatements` is append-only, idempotent DDL**: one statement per entry, `CREATE TABLE IF NOT EXISTS` / `CREATE [UNIQUE] INDEX IF NOT EXISTS`, `auth_`-prefixed tables, so `migrate` is safe on every deploy and on every cold start. `authTableNames` is derived from these statements, and the Alchemy `AuthSchema` resources list and drop the tables through it.
- **Codecs**: instants are epoch milliseconds in `BIGINT` (an `INTEGER` overflows Postgres int4), booleans `0`/`1`, attribute bags JSON `TEXT`, binary values base64 `TEXT`.
- **Token columns hold the digest the service computed** (`auth_sessions.id`, magic-link, verification and reset tokens, `auth_api_keys.key_hash`). The store never hashes and never sees a raw bearer token.
- **Atomicity is per statement**: upserts and counters are a single `ON CONFLICT … DO UPDATE` or `UPDATE … RETURNING`, never read-modify-write. Multi-step writes (challenge, OAuth state, `emailOtp.upsert`, `identifier.replace`) run in `sql.withTransaction`; on D1 it becomes `batch()`es, atomic between reads but not across one (see effect-auth-alchemy-cloudflare), so a multi-step write must stay safe when interrupted between its statements: `identifier.replace` claims the new value before it releases the old one.
- **Store contract**: a miss is `null`; any driver failure becomes `AuthError` with the cause kept; methods carry `R = never` (the `SqlClient` is read when the store is built).
- **Unique indexes are the claim mechanism** (`auth_identifiers (type, value)`, `auth_oauth_accounts (provider, provider_id)`, `auth_api_keys (key_hash)`): a violation surfaces as `AuthError` and the services turn it into the domain error.
- **Expired magic-link and email-OTP rows, and rate-limit rows whose window and block have both passed, are deleted only by `purgeExpired`**, which the host schedules (#420, #686); a rate-limit row inside its window or still blocked stays. `purgeExpiredWith({ limit })` caps each table's `DELETE` at `limit` rows (`WHERE <expired> AND <key> IN (SELECT <key> … WHERE <expired> LIMIT n)`, a row value for `auth_email_otps`' composite key; the outer `<expired>` keeps a row refreshed concurrently after the subquery picked it, which PostgreSQL READ COMMITTED would otherwise delete) and is `purgeExpired` without one (#729). No store sweeps on write and no table carries a TTL. `auth_email_otp_failures` (the failure budget, #590) has no expiry and `purgeExpired` leaves it: only `clearFailures` deletes a row. `purgeExpiredKV` is the same rule for the `KeyValueStore` stores (#709): `KeyValueStore` has no per-entry TTL, so a `rate-limit:` entry stays until the purge finds its window and block both passed (`<=` now); the OTP failure-budget keys sit outside the prefixes it sweeps.
- **Authorization is not in `layer`**: `RbacEntityResolverLayer` (roles as `Role::` parents of `User::`) and `readRbacPolicies` (compiled by `Auth.Rbac.policies`) are wired into an `Authorizer` by the application. There is no second evaluation path.
- **`layer` covers a fixed store set**; stores added to the core later (one-time tokens, trusted devices, phone OTP, organizations, the OIDC provider, SSO, device authorization) are not implemented here yet. Adding one means a table in `sql/Schema.ts`, `make*Store` + `*StoreLayer` in `sql/Stores.ts`, an entry in `layer`, and a run of the shared suite on both engines.
- The PostgreSQL suites open their databases from one migrated PGlite template per run (`vite.config.ts`'s `globalSetup`, `src/sql/testing/`); Vitest's file-system module cache is off for this package because of it (#502).

### `./saml`

- **Never relax `@node-saml/node-saml` below `5.1.0`**: the fix for CVE-2025-54419 / CVE-2025-54369 (profile data read from bytes the signature did not cover). `xml-crypto` is a dev dependency for the fixtures only.
- **Trust only pinned certificates** (`idpCertificates`), never a `KeyInfo` in the document; profile data is read only from signature-covered XML.
- **Every check is a rejection, never a warning**: issuer, audience, `Conditions` window with `defaultClockSkewMs`, `Recipient` and `Destination` equal to the ACS URL, `SubjectConfirmationData` `NotOnOrAfter`, signed `InResponseTo` agreeing with every `InResponseTo` in the raw XML (never node-saml's `profile.inResponseTo`, which 5.2 fills from the signed value, #532), at most one `Assertion`, no duplicated `ID`.
- **Algorithms are allow-listed** (`defaultSignatureAlgorithms`: SHA-256 and SHA-512); HMAC signature methods are refused outright.
- **Encrypted assertions are refused** with an actionable message; there is no half-built decryption path.
- **Pre-flight scans are conservative**: they run over the whole decoded document before node-saml and reject if anything anywhere fails, decoys included. Don't narrow them to "the signed part".
- **The request-only placeholder certificate** (`REQUEST_ONLY_IDP_CERT`) is used only to build an `AuthnRequest`; `verify` always builds its own instance from the pinned certificates.
- **Replay is the `SsoService`'s job** (`SamlReplayStore`, spent once per `AuthnRequest` and per `Assertion`); `./saml` is stateless.
- Every failure is a `SamlError`. `saml/Verifier.test.ts` reproduces each attack shape against hand-built signed fixtures; a new check gets a fixture.

### Root

- **Services are `Context.Service` classes with a static `layer`**; stores, hooks and `SecureRandom` / `Digest` are resolved once in the module-scoped `make`, so service methods carry `R = never`. Implementations are typed `typeof X.Service`; there are no `*Shape` interfaces.
- **Stores are dumb persistence**: a lookup returns `X | null` on a miss and fails only with `AuthError` (infrastructure). Services turn a miss into a typed domain error.
- **Services read identifiers by value only through `lookupIdentifier`** (#602), never `IdentifierStore.getByValue` directly: it treats a record whose `type` or `value` differs from the one asked for as a miss, so a store that compares loosely (a MySQL `_ai_ci` collation) cannot redirect a flow to another account. A flow that delivers to a resolved identifier sends to `identifier.value`. `Identifier.test.ts` fails on a direct `.getByValue(` outside the store implementations.
- **Errors**: domain errors are `Data.TaggedError` with a stable `code` (`Errors.ts` when two modules raise them, else module-local); HTTP-boundary errors are the `Schema.TaggedError` classes in `http/HttpApiSchema.ts` with fixed statuses (`RateLimitError` → 429, `AuthError` → 500). Nothing subclasses `AuthError`.
- **Bearer secrets are stored as SHA-256 digests** (`hashToken` and its wrappers, ADR-0004): session ids, magic-link, email-verification, password-reset, invitation and one-time tokens, device codes, API keys, OIDC codes and tokens, email / phone OTPs, backup codes. The raw value goes to the user once; the digest is the store key.
- **An invitation is accepted or rejected only with its emailed token or from a verified matching address** (#586, #673): `Invitation.tokenHash` is the digest of a 256-bit token minted per send (a resend replaces it) and handed only to `sendInvitationEmail`, which `inviteMember` requires. A wrong token answers "not found". Without a token (`InvitationResponseInput.token` omitted), only a user whose matching email identifier is already _verified_ may answer by id; anyone else the invitation is not addressed to gets "not found" (the id confirms nothing), and an unverified match is refused and must bring the token. For an unverified email identifier the token is the address's first proof and goes through `proveAddress` (password and other credentials cleared, every session but the accepting one revoked), never a bare `setVerified`; the id path never calls `proveAddress` and never promotes an identifier. The HTTP tier takes the token as the optional input-only `token` attribute of `PATCH /invitations/:id` and never returns it or its digest; `GET /invitations` (`listInvitationsForUser`, #706) lists only the caller's pending, unexpired invitations to their own _verified_ email identifiers, the set they may answer by id, never another user's. An organization's invitation list is read with `invitation:create` (#715): `listInvitations(actorId, organizationId)` goes through `requireMemberPermission`, as `inviteMember` does, so a non-member, a member without it and an unknown organization are refused alike (`GET /organizations/:id/invitations` answers each the same `403`) and the answer reveals no ids. The invitee gets the accepted invitation from `acceptInvitation` (`{ member, invitation }`), never by reading the organization's list.
- **Secrets compare in constant time** with `constantTimeHashEqual` / `timingSafeEqualBytes` (`TokenHash.ts`).
- **A send that would reveal whether an account exists never sits on the response path**: those flows hand it to `DeliveryScheduler` (`makeDetachedSend`), and its failure goes to the `afterDeliveryFailure` hook and the delivery metric, never to the caller. Every other send is awaited (#196).
- **Randomness comes from the `SecureRandom.SecureRandom` service** (`effect/crypto`; default `PlatformCrypto.layer`, Web Crypto, which also provides `Digest.Digest`); never `Math.random`. Its error channel is `never`, so a draw is never mapped to an `AuthError` (#520). Direct `node:crypto` stays in `password/Password.ts` (scrypt), `TokenHash.ts` and `Cipher.ts`.
- **The core runs on Workers with `nodejs_compat` at compatibility date 2023-01-01 or later** (#748; the README's Runtimes section states it). So nothing outside `./saml` reads a Node global: the corral imports `Buffer` from `node:buffer` (lint bans the global there too, `vite.config.ts`), and no `process` or `global`. workerd's `node:crypto` refuses a `KeyObject` beside options (`{ key: KeyObject, dsaEncoding }` is `ERR_INVALID_ARG_TYPE`), so `Cipher.ts` passes the PEM or `{ key: jwk, format: "jwk" }` there, and from 2025-12-03 its JWK export carries absent members as `undefined`, which `generateJwsKeyPair` drops before it checks that `kty`, `crv`, `x` (and `y` for ES256) are present, throwing an `AuthError` when one is not. `Workerd.test.ts` runs every corral primitive inside a real workerd at 2023-01-01 and at workerd's newest date; a new `node:*` call joins it. `Cipher.test.ts` keeps the pre-#748 `KeyObject` JWS as the reference the current one must match.
- **The first proof of an email address clears the account** (#425, #440, #694, #704): a flow that promotes an unverified email identifier to verified on a proof (the verification link, magic link, email OTP, invitation token, Google One Tap, SSO, OAuth sign-in) goes through `proveAddress` (`FirstProof.ts`), which first clears the password, removes the account's unverified phone identifiers (a verified phone was proven by its holder and stays), deletes every other credential the account holds (OAuth account links, passkeys, API keys, the multi-factor enrolment, trusted devices, the OIDC provider's access and refresh tokens through `OidcTokenStore.deleteByUserId`) and then revokes the sessions; JWTs already issued (`Jwt`) cannot be revoked and are left to expire; an identifier already verified is promoted with nothing removed. The credential stores are optional: each caller resolves its `FirstProofServices` once with `firstProofServices` (the credential stores through `Effect.serviceOption`) where it resolves its other stores, so an app without one sweeps the rest. OAuth creates the link being made only after `proveAddress`, so it survives. `FirstProof.test.ts` holds a case per credential kind; a new credential store joins `FirstProofCredentials` and gets one. One policy holds for every IdP-backed path (#671): a provider-verified email that matches an unverified local address proves it, then links. A new promoting flow calls it.
- **Deleting a user deletes everything the account holds, the user row last** (#601). Every path that deletes a user (`AccountManagementService.confirmAccountDeletion` / `POST /account-deletions/redemptions`, `AdminService.removeUser` / `DELETE /admin/users/:id`, `AnonymousService.linkAccount`, and `UserService.deleteUser` through the `AccountDeletion` service) goes through `purgeUser` (`UserPurge.ts`, internal): the per-user delete of every user-keyed credential and token store present where the layer is built (`userCredentialStores` in `UserCredentials.ts`, through `Effect.serviceOption`, with `AccountManagementStore` passed by the caller because `AccountManagement.ts` imports the module), then the address-keyed proofs sent to each of the user's identifiers (`MagicLinkStore.deleteByEmail`, `EmailOtpStore` / `PhoneOtpStore.delete` for every purpose; failure budgets stay), then `invalidateUserSessions`, then `IdentifierStore.deleteByUser`, then `UserServiceStore.delete`. A new path that deletes a user goes through it and gets a case in `UserPurge.test.ts`; a new address-keyed proof store joins `AddressProofStores`. No foreign keys, no cascade, no transaction of the services' own: a failure leaves the user row, never orphans, and a retry finishes; an app whose stores share a transaction wraps the call in it (`sql/Stores.test.ts` pins that the `./sql` stores join an ambient `sql.withTransaction`). Each user-keyed store contract carries a required `deleteByUserId` (`MultiFactorStore`'s `delete(userId)` is its per-user delete) and a conformance suite checking it deletes that user's rows only; a new user-keyed credential store joins `UserCredentialStores`, `deleteCredentials` (and `FirstProofCredentials` when a first proof should clear it too), gets that suite, and a row in `UserPurge.test.ts`. `UserService.deleteUser` delegates to `AccountDeletion` (`AccountDeletion.ts` holds only the tag, so `User.ts` imports no store: the stores' modules import `User.ts`, and the reverse would be a cycle; its layer is `AccountManagement.ts`'s `accountDeletionLayer`), resolved with `Effect.serviceOption`, and without it fails with `AuthError` rather than delete the row alone. SCIM's `DELETE /Users/:id` deactivates and deletes nothing. `ApiKeyService.verify` / `verifyWithRateLimit` answer `Invalid API key` for a key whose owner `UserStore` does not find or is banned or SCIM-deactivated (`UserStanding.ts`, #755), so `ApiKeyService` requires `UserStore`. `./sql`'s `UserServiceStore.delete` removes the user's `auth_user_roles` rows with the user in one transaction.
- **OAuth auto-links only a provider-verified match** (#588, #671, ADR-0007 as amended): `signInWithCallback` links a new provider identity to the user holding its email only when the provider reports `email_verified: true` and `autoLinkByVerifiedEmail` (default `true`) or `trustedProviders` applies. A verified local address links as it is; an unverified one goes through `proveAddress` first (password and other credentials cleared, sessions revoked, address verified), and only then are the account linked and the session minted. Any other match (an unverified provider email, auto-linking off for an untrusted provider, a dangling identifier) fails with `EmailInUseError` and changes nothing: no link, no session, no `proveAddress`. `trustedProviders` never waives the provider's `email_verified`. `OAuthService` therefore requires `EmailPasswordStore`.
- **WebAuthn challenges are bound to their ceremony** (#591): a `WebAuthnChallenge` carries `ceremony`, and each verify refuses the other ceremony's challenge; `verifyRegistration` takes the signed-in user's id and refuses a challenge issued to anyone else. A store reads a challenge with no known ceremony as `null` (`Testing.challengeStoreConformance`; in `./sql` the ceremony is its own table, `auth_webauthn_challenge_ceremonies`). `userVerification: "required"` is enforced in both ceremonies, the results report UV and the backup flags, and registration stores the attested credential id (equal to the response's, never one already registered).
- **A sign-up never stores an authority-bearing attribute** (#580): `EmailPasswordService.signUp` (after the `beforeSignUp` hooks) and `AuthLifecycleService.signUp` strip `UserServiceConfig.serverOnlyAttributes` and `SIGN_UP_PROTECTED_ATTRIBUTES` (ban, SCIM, `isAnonymous`) from every new user and stand-in; `POST /users` keeps only `Http.make`'s `signUpAttributes` keys (default none, others dropped silently) within `SIGN_UP_ATTRIBUTES_MAX_BYTES`. A new key that another privileged flow owns joins `SIGN_UP_PROTECTED_ATTRIBUTES`; a new path that creates a user from caller input strips the same set.
- **Callback state is single-use** (#685): every OAuth and OIDC SSO callback (`OAuthService.handleCallback` / `signInWithCallback` / `linkAccount`, `SsoService.handleCallback`) spends its `state` with `OAuthStateStore.consume`, an atomic get-and-delete, before anything else (before the code exchange, before the expiry and provider checks), so a replay fails whether the first use succeeded or failed, and of concurrent callbacks with one state only one passes. There is no `get` / `delete` on the store to read a state without spending it. `consume` is one `DELETE … RETURNING` in `./sql` (D1 included) and runs under a store-owned semaphore in `oauthStateStoreKV` (atomic per process only). The SAML `RelayState` is single-use through its `AuthnRequest` record (`SamlReplayStore.consume`). `Sso.test.ts`, `oauth/OAuth.test.ts`, `KeyValueStores.test.ts` and `sql/Stores.test.ts` hold the replay cases (`#685`); a new callback flow joins them.
- **Session ids are 160 bits** (`crypto.randomBytes(20)` in `SessionService.ts`), with active and idle expiry.
- **`Session.id` is always the stored id (the token's digest), never the token** (#581). `createSession` returns `Types.IssuedSession` (`{ session, token }`) and every sign-in result carries `token` beside `session`; `validateSession` and `invalidateSession` take the raw token, `revokeSessionById`, `revokeOtherSessions` and `setSessionAttributes` take the stored id, and `afterSignOut` observes the stored id. Hooks, `CurrentSession`, the cache cookie's payload and every session the services answer hold only the digest.
- **No hook ever sees a raw session token** (#669). `beforeValidateSession`, `beforeSignOut` and `afterSignOut` receive the stored id (`hashToken(token)`), and every other hook that carries a session sees `Session.id`, the digest; `SessionService` hashes the presented token before it fires any hook. The two `before*` session hooks are observe-or-deny: failing refuses the operation, and their return value is never read back, so a plugin cannot rewrite the token or redirect the lookup or sign-out. `SessionService.test.ts` ("no plugin observes the session token through any hook") stacks a spy on every hook point; a new hook that carries a session must hold only the digest.
- **No response body carries a session token** (#581). The HTTP tier writes the raw token only to the `HttpOnly` session cookie (and the multi-session device list cookie) and, in bearer mode (`cookie.bearerMode`), the `set-auth-token` header (`decorateSessionResponse` is the one place); every `sessions` / `device-sessions` / `impersonations` resource is named by the digest. `HttpServer.test.ts` ("the session token never reaches a response body") searches each issuing response's serialized body for the cookie's token; a new session-issuing endpoint joins it.
- **Sign-in does constant work**: password verification runs against a cached decoy hash when the account does not exist.
- **One-time codes are budgeted per address, not per code** (#590). `EmailOtp` and `PhoneOtp` share `OtpCode.ts` (internal): every wrong code is counted against the (address, purpose) pair through the store's `recordFailure`, in a budget kept apart from the code's record so a resend (`upsert`), `delete`, expiry and `purgeExpired` never reset it; only a successful verification (`clearFailures`) does. `send` waits out the longer of `resendCooldown` (default 60 s) and the backoff (after 5 wrong codes, one minute doubling per wrong code, capped at a day). Backoff only, never a lockout: a send succeeds once the delay has passed. The gate reads the same record and budget for an address with and without an account, so it reveals nothing. Every store implementation (`EmailOtpStoreKV`, `./sql`, `Testing.memoryPhoneOtpStore`, the D1 package through `./sql`) runs `emailOtpStoreConformance` / `phoneOtpStoreConformance`.
- **Every passwordless send has a resend cooldown on by default** (#590, #682): `resendCooldown` is 60 s for the email and phone OTPs, the magic link and `EmailVerificationService.resendVerification` (measured from the user's newest token, `EmailVerificationStore.getLatestByUserId`); `0` turns it off. A send inside it fails with `ResendTooSoonError`. Where that answer would tell an unverified account from an unknown address (`POST /email-verifications`, the `AuthLifecycleService` sign-in and duplicate sign-up resends), the caller swallows it and answers as for any other address.
- **Every unauthenticated send is capped per recipient** (#684): `RecipientSendLimit.ts` (internal) counts sends per (purpose, recipient) through the `RateLimiter` over the `RateLimitStore`, 5 an hour by default (`recipientSendLimit`; `false` turns it off), in the email and phone OTPs (every purpose), the magic link, `requestPasswordReset` and `resendVerification`; a send past it fails with `RateLimitError`. The key is `recipient-send:<purpose>:<hashToken(normalized address)>`, never a raw address. Each flow counts after its cooldown and backoff gates pass and whatever the address lookup finds (the reset before it), so an unknown address is capped exactly as a known one; where the answer would still tell them apart (`POST /email-verifications`, the `AuthLifecycleService` resends) the caller swallows it (`isRecipientSendCapped`). A new flow that sends to an address the caller names joins the cap and `RecipientSendLimit.test.ts`.
- **Every credential-verifying flow fires `beforeAuthenticate`** (#592, #678): email and password, username, email OTP (sign-in and `EmailOtpService.check`, every purpose), phone OTP, magic link, passkey (`WebAuthnService.verifyAuthentication`) and second-factor redemption (TOTP, backup code, OTP second factor), after resolving the handle to a user and before checking the credential or spending a code, link or challenge. A new sign-in method or second factor fires it too. The abuse plugins (lockout, captcha, per-account and per-IP rate limits) guard it, never `beforeSignIn`, which only `EmailPasswordService.signIn` fires and which exists for input rewriting. Per-account plugins key on `authenticationSubject` (the resolved user, else the handle).
- **An attempt that names no account still reaches the gate** (#678): an unknown or expired second-factor challenge, magic-link token or passkey challenge, or an unknown passkey credential, fires `beforeAuthenticate` unkeyed (no `identifier`, no `userId`) and then fails, so `IPRateLimitPlugin` counts guessed tokens. `authenticationSubject` answers `undefined` for it and every per-account plugin lets it through; a per-account plugin never invents a key for it.
- **Possession proofs are exempt from the account lock** (#678, #698): `AccountLockoutPlugin` neither refuses nor counts an email OTP, phone OTP or magic-link attempt (`isPossessionMethod`), nor a passkey attempt (an unguessable signature over a non-secret credential id; it stays under the IP limit), so knowing a handle cannot block the owner's recovery. That holds only while their own bounds hold: the per-code `maxAttempts`, the per-address failure backoff (#590), 256-bit magic-link tokens and the rate limits. Never loosen one of those without revisiting the exemption; `BeforeAuthenticate.test.ts` pins that a locked account's handle buys an attacker no guesses past them.
- **Lockout clears only on a session the user earned**: `afterCreateSession`, never a sign-in that issued only a second-factor challenge, and never an admin impersonation (`isImpersonationSession`: `attributes.impersonatedBy`, #678). A new flow that issues a session on someone else's behalf marks it so too.
- **Every code and link send fires `beforeSendCode`** (#678): `EmailOtpService.send`, `PhoneOtpService.send` and `MagicLinkService.send`, with the caller's `captchaToken`, before the address is looked up or anything is stored or sent, so a refusal reveals nothing about the account. `CaptchaPlugin`'s `"sendCode"` endpoint (default on) guards it; `POST /otp-challenges` carries `captchaToken` and answers a refusal with the hook error's status.
- **One authorization model** (ADR-0018): every decision goes through `Policy.decide`; `Rbac`, `Protected`, `OwnedAccess` / `ReferenceAccess` read scopes and `Ladder` axes compile to or project the kernel. Default deny, forbid overrides permit. `Ladder.hasAtLeast` is for UX gates, never the gate.
- **Owned and reference reads fail closed** (#637): a row with no owner (or no followers-of account, or no group) never becomes an entity ref with an empty or sentinel id, and `IsFollower` / `IsMember` are never asked about it; an unprovided seam answers `false`; `draft` and `unapproved` are present booleans in the decision slice, so a NULL reads as unpublished. `AccessParity.test.ts` holds the parity matrices (`canView`, `readScope`, `ReadScope.compile` over `policies` + `binding`, `serveableAxes`); a new axis gets a column there.
- **No granting beyond your own permissions** (#585): `Organization.ts`'s `requireGrantable` / `requireOutranks` gate every role write. An actor assigns a role (`addMember`, `inviteMember`, `updateMemberRole`) only when their role carries every permission it carries, and changes, deactivates, reactivates or removes a member only when it carries every permission of that member's role (`previousRole` for a reactivation); a wildcard grant is satisfied only by a wildcard at least as wide. A role string nothing resolves is rejected on every write path. This covers the owner role and custom roles alike; don't add a path that writes `member.role` or `invitation.role` around them (JIT and SCIM write the organization's `defaultRole`, which `setDefaultRole` validates). Custom-role writes follow the same rule (#673): `upsertOrgRole` needs the actor to hold every permission of the new definition and every permission the name resolves to now (custom or static, `requireHoldsCurrent`), `deleteOrgRole` every permission of the definition and of the static entry it falls back to, and neither may touch the actor's own role (`ensureNotOwnRole`). The default owner role is `*:*`, so an owner can grant, define and remove any custom role; it stays protected from redefinition.
- **Every organization-scoped read takes an actor and is refused alike for a stranger and an unknown id** (#717): `getFullOrganization(actorId, organizationId)` (behind `GET /organizations/:id` and `GET /organizations/:id/members`), `listTeams`, `listTeamMembers`, `listTeamsForMember`, `listDomains` and `listOrgRoles` go through `requireMembership` (any _active_ member; a deactivated one is a stranger), and a read that needs more goes through `requireMemberPermission` (`listInvitations`, with `invitation:create`, #715). An unknown organization has no member, so it fails with the same `OrganizationError` a stranger gets, and the HTTP tier answers both through `asOrganizationActor` with the same `403` and body: the answer never confirms that an id exists. `listOrganizations` lists only active memberships, so it never shows an organization its caller may not read. `PATCH /organizations/active` records an organization on the session only after `requireMembership` (#576), refusing a stranger, a deactivated member and an unknown id with that same `403`; `data: null` clears it without a check. A new organization-scoped read joins this list; never add one that takes only the organization id. The same holds for a record looked up by its own id (#718): an unknown id gets exactly the refusal another tenant's record and a member without the permission get, never a `404` or a "not found". In the service, `requireTeamPermission` and `listTeamMembers` refuse an unknown team as their check refuses a stranger, and `cancelInvitation` / `resendInvitation` check the permission before the invitation's status, so only a permitted member learns it is no longer pending; the refusals are `Organization.ts`'s `missingPermission(permission)` (`Missing permission '<permission>' in this organization`) and `notAMember()` (`You are not a member of this organization`). In the HTTP tier, `organizationTarget` (behind `/organization-members/:id`, `/organization-domains/:id`, `/organization-roles/:id` and `/team-members/:id`) fails an id that names no record with the refusal the operation gives a stranger (`missingPermission` of the permission it needs, `notAMember()` for `GET /organization-members/:id/teams`), and every operation behind it checks that permission before anything else. The id-only lookups (`getMemberById`, `getTeamMemberById`, `getOrgRoleById`, `getDomainById`) check nothing: a new caller answers their `null` with that same refusal. `HttpServerModules.test.ts`, `DomainAttestation.test.ts` and `Organization.test.ts` compare status and body (`#718`); a new id-addressed route joins them.
- **An empty entity id or type names no entity** (#661, #666): `Entity.EntityRef` decodes only a non-empty `type` and `id`, and `Entity.namesEntity` checks both; a hand-built ref with either empty equals nothing, itself included (`refEquals`, `attributeValueEquals`, `entityIn`), and no type scope matches it (`isType("")` included); `Policy.decidePure` / `decide` deny a request naming one as principal, action or resource with reason `"invalid-request"`, before any policy runs (`Policy.isWellFormed`); `ReadScope.compile` gives `deny` for such a principal or action and never compiles such an entity value to an `Eq` atom; `Guard.make` reads an empty-id viewer as anonymous. The library's own row stand-ins (`ReadScope`'s placeholder, `Guard` / `OwnedAccess` / `ReferenceAccess`'s decision resource) use the id `"row"`, which no policy reads. An anonymous caller is `Anonymous::"anonymous"`, never an empty id or type. `EmptyEntityId.test.ts` and `EmptyEntityType.test.ts` hold both paths, and `ReadScope.test.ts`'s parity corpus has empty-id and empty-type viewers.
- **System principals are denied by default** (ADR-0019): only a permit whose principal scope names the `System` type can allow one; role permits never match one.
- **404 until configured**: an optional HTTP feature resolves its service with `Effect.serviceOption` and answers `404` when the layer is absent.
- **Every response carrying `Set-Cookie` is `Cache-Control: no-store`** (#628), so a shared cache never replays one browser's session to another. In `http/HttpServer.ts` the two cookie writers mark it (`setResponseCookie` and `decorateSessionResponse`, through `withNoStore`), so the exported group layers keep the rule outside `Http.make`, and `Http.make`'s handler holds it for every response it serves (`noStoreWithSetCookie`); `RemoteSession.relayResponse` and `withSetCookie` mark what they relay, and `relayResponse` marks a response whose `Set-Cookie` it strips for a machine caller too (it answered that caller's credential). The merge is `http/CacheControl.ts`'s `mergeNoStore`: an existing `no-store` is kept, any other `Cache-Control` keeps its directives with `no-store` appended. Handlers whose body hands a credential or a per-caller single-use value over (the current session, `POST /tokens`, API-key and OAuth-client creation, the MFA secret and backup codes, the second-factor challenge a `POST /sessions` answers, `POST /device/code`, the token endpoints, `POST /oauth2/consent`, userinfo, dynamic registration, `POST /sso-authorizations`' state, `POST /google-one-tap-nonces`) mark it with `noStore` whatever they answer, and under `Http.make` the token endpoints (`/oauth2/token`, `/device/token`) are marked by router middleware before the payload is decoded, so a malformed request's `400` is `no-store` too (RFC 6749 §5.2); the public documents (JWKS, discovery) stay cacheable. A new cookie writer goes through `setResponseCookie` or `decorateSessionResponse`, and a new credential-bearing handler yields `noStore`; the `#628` cases in `HttpServer.test.ts` and `RemoteSession.test.ts` pin both.
- **An API key resolves only from its header, and never through a session** (#730). `GET /api-keys/current` resolves its `ApiKeyService` first (`404` without one, before anything is read), reads the key only from `cookie.apiKeyHeaders` (default `x-api-key`; never the URL, never the cookie or bearer token, so a key always wins), and verifies it with `verifyWithRateLimit` and no required permissions. **Each resolution consumes one use of the key** (`remaining` decrements, `lastUsedAt` moves); a non-consuming check is #645. Every key that does not resolve (unknown, disabled, expired, exhausted, missing, an owner gone, banned or SCIM-deactivated; the owner is judged in `verify`'s lookup, before the limiter and the spend, #755) gets one identical `401` (`refuseApiKey`, detail `Invalid API key`), the reason only in the server log and the key in no log line or body; only `reason: "rate-limited"` answers `429` with `Retry-After`, and `verifyWithRateLimit` consumes the per-key bucket only after the enabled / expiry / remaining / permission checks pass, so a disabled, expired or exhausted key over its limit still gets the identical `401` (never reorder them); every answer is `Cache-Control: no-store`, and the `200` carries the `api-keys` projection (`apiKeyResource`), never the hash or plaintext. `RemoteSession.resolveAtEdge*` sends a key-bearing request there and never forwards the cookie on that call: a `401` is anonymous, any other answer fails closed (or degrades), never falling back to the cookie. `http/ApiKeyResolution.test.ts` pins all of it.
- **The `Set-Cookie` relay withholds cookies only from a machine caller** (#619): `Http.RemoteSession.relayResponse` (and `relay` through it) strips `Set-Cookie` when the inbound request carries an API key or a bearer token, a session cookie beside it or not, and relays it to every other caller, so a browser with no cookie yet receives its session cookie on first sign-in. Never make a session cookie a condition of receiving one. `RemoteSession.test.ts` holds each inbound shape.
- **`Http.make` fails at startup, not per request**, when a configured limit has no `RateLimiter` (`RateLimiterConfigError`) or an address-keyed limit (`ipRateLimit`, `IPRateLimitPlugin`, dynamic client registration) has no `trustedProxy` (`ClientAddressConfigError`). `allowMissingClientIp: true` is never an address source and never waives the check (#682): with no proxy a Web `Request` has no address, so the limit would refuse every request, and a handler must never start that way. With `strict: true` it also refuses a `services` build that cannot finish synchronously (`ServicesBuildPendingError`).
- **Client IP resolution never keys on a client-chosen value** (`ClientIP.ts`, #584): forwarded headers are read only under a `trustedProxy`; `hopCount` counts from the socket address when there is one and from the header's end when there is none (a Web `Request`, as `Http.make` serves), so prepended entries never move the result; every header entry used is parsed as one IP literal (`parseIpLiteral`), and a selected or trusted entry that is not one resolves `undefined` (a `429` on limited endpoints), never a key. `ClientIP.test.ts` covers both the socket and the socket-less chain; a change to the chain arithmetic gets a case for each.
- **The per-endpoint IP limit is on by default** (#583): `ipRateLimit` omitted means `defaultEndpointRules`, so `Http.make` needs a `RateLimiter` and a client address source unless it is given `ipRateLimit: false`, the only opt-out. The defaults stay; a deployment changes one endpoint's limit with a rule ahead of `...defaultEndpointRules` (the first match wins, #682). A new unauthenticated endpoint that sends a message, writes a row, calls out or verifies a secret (or an authenticated one that hashes a password) gets a default rule and a row in `HttpServer.test.ts`'s `LIMITED_ENDPOINTS`.
- **Rate-limit rules match the endpoint the router matched**, by its path template and method (`endpointRateLimit`, router middleware on every auth route), never the raw request path (#582): the router is case-insensitive and ignores trailing, duplicate and percent-encoded spellings, and every spelling must count in the endpoint's bucket. A check on the raw pathname may only fail closed (the mount `prefix` gate answers `404` for a spelling it does not know).
- **Optional encryption secrets fail closed when set but empty** (`OptionalSecretConfig.ts`): `JWT_ENCRYPT_PRIVATE_KEY_SECRET`, `OAUTH_ENCRYPT_TOKENS_SECRET`, `TWO_FACTOR_ENCRYPT_SECRET`.
- **A tenant proves a domain only through DNS; manual attestation is the operator's** (#598). `OrganizationService.addDomain` always makes a `dns` claim (the HTTP payload refuses `verificationStrategy: "manual"` with `400`), and `verifyDomain` runs only the `DomainVerifier` check: `domain:manage` is never the proof, and an unverified `manual` claim is refused. A `manual` claim comes only from `attestDomain(organizationId, domain, { attestedBy })`, a server-side call with no actor, exposed only at the admin-gated `POST /admin/organization-domains`, which records the admin as the claim's `attestedBy` (#680); the operator's `releaseDomain(organizationId, domain)` removes any claim whatever its state, exposed only at `DELETE /admin/organization-domains/:id`. Never wire either to a route an organization member can reach. Claims are unique per `(organizationId, domain)`, and at most one per domain is `verified` (`OrganizationDomainStore.getVerifiedByDomain`, which JIT provisioning reads): `addDomain` consults only the organization's own claims, so it never reveals another tenant's claim and a pending claim squats nothing.
- **Every platform-admin HTTP gate is the `AdminService`'s rule** (#680): `requireAdminCaller` (the OAuth-client, SSO-provider and domain attestation and release endpoints) asks the mounted `AdminService.isAdmin`, so a custom `AdminConfig` (`adminRoles`, `adminUserIds`) governs them as it does `/admin/users`; only without an `AdminService` does it fall back to the default `isAdmin` (role `admin`). A new admin-only endpoint gates through `requireAdminCaller`, never a direct `isAdmin(user)` call, and the gate runs before any lookup, so a non-admin never learns whether an id exists.
- **JSDoc `@example`s are type-checked and run** by `vp run docs`: in-memory stores, inline config, no network, no `declare` stubs; failure is a throw or a failed `assert`.
- No change may weaken timing safety, token entropy, cookie flags, the trusted-origin CSRF check or replay protection (DESIGN.md ground rules).

## Terms

- **Credential / Verification / Auth state** — the three entity categories (ADR-0006): a persistent registered means of authenticating (Account, Passkey, ApiKey, MultiFactorEnrollment, TrustedDevice), a single-use artifact proving possession (tokens, OTPs, BackupCode, OAuthState, WebAuthnChallenge, Invitation), and the record of having authenticated (Session, JWT).
- **Account** — a User's link to one Provider; the `credential` provider holds the password hash.
- **Identifier** — a login handle (`email`, `username`, `phone`) in the `IdentifierStore`, unique per `(type, value)`; not a User field (DESIGN.md D12).
- **Hooks / plugin** — `before*` / `after*` hook points; a plugin is a layer composed with `composePlugins` (first-party ones keep the `*Plugin` suffix).
- **Seam** — a service the core declares and an adapter or the host implements: `PasswordHasher`, `EmailSender`, `SmsSender`, `DeliveryScheduler`, `SamlVerifier`, `SecondFactorGate`, `EntityResolver`, `IsFollower`, `IsMember`.
- **Principal / entity** — the kernel's typed references (`Type::"id"`); a **system principal** is `System::"<name>"`.
- **Ladder / rung / axis** — an ordered role list, one role per user, and a named "this rung or above" capability.
- **Fail-open / fail-closed resolution** — `SessionResolution.resolveFailOpen` turns a session-service fault into an anonymous request reported as `degraded`; `resolve` fails. Neither is the default.
- **Session Atoms (client)** — `SessionAtoms` from `makeSessionAtoms(client)` (`./client/atoms`): `result` (`AsyncResult`), `state` (`{ data, isPending, error }`), `data`, `isSignedIn`, `isPending`, `error`, `sessions`, `sessionsState`; what the Svelte binding adapts. Not the server-side `SessionStore` service.
- **Session observer** — an `onSessionChange` listener; the session Atoms register one while mounted.
- **Mutating call** — a client request that changes the session, followed by notifying the session observers (`AuthClientPluginContext.mutating`). A client **plugin** is `definePlugin(install)`, adding typed methods via `client.extend`.
- **Store layer** — `./sql`'s `<Name>StoreLayer`: `Layer<Auth.<Name>Store, never, SqlClient>` over `make<Name>Store`.
- **RBAC tables** — `auth_user_roles` (user → role) and `auth_role_permissions` (role → `resource`/`action`); data for the kernel, not a store service.
- **IdP / SP** — the identity provider that signs a SAML assertion, and this application as the service provider (`spEntityId`, `acsUrl`). The **ACS URL** is the endpoint the `Response` is posted to; **RelayState** is the opaque `state` issued with the `AuthnRequest` and echoed back.
